# PM 执行现场与检查点

## 使用方式

在任务详情点击「核实原节点」。新版任务会显示最后保存的阶段、检查点版本、已完成数量、执行待核实数量和未派发数量；若保存过交付确认，会提示继续核对任务验收记录。

这些信息描述最后一次成功保存的现场，不代表节点当前仍在执行或外部工具已经停止。新版任务可在「核实恢复条件」后申请「恢复原任务」，具体限制见下文。旧版任务没有执行现场记录时，仍可核实启动回执；记录缺失不证明没有执行。

若显示「检查点写入失败」，当前 PM 已停止后续调度。请检查原节点磁盘空间、文件权限和日志，保留原数据，核对在途工具与交付物。修复磁盘后不会自动重启该 PM，也不要删除启动回执来强制重做。

## 保存内容与顺序

- 启动工作线程前保存任务、原 Secretary 地址、设备身份与开始时间。
- 需求细化、澄清问题/回复、计划生成，以及进入执行和聚合时保存阶段。
- 子任务实际执行或发送请求前，保存执行编号、归属、目标节点和完整请求；直接执行也使用已落盘的执行编号。
- 接收终态结果后，先保存原始回报，再进行质量检查。成功输出落盘后才释放依赖任务。
- 重试保留旧执行编号、回报、重试次数和接管状态，新的执行编号必须先写盘。
- 聚合结果、交付请求全文、准备发送与匹配确认分开保存。准备发送记录不证明 Secretary 已接收；确认未保存时保留待核实语义。
- 取消/暂停/失败保存停止状态。晚到回报不解除停止，停止后的旧阶段不能将检查点改回监控。

检查点写入失败、序列化失败、归属不符或版本冲突都会停止后续调度；已发出的请求和工具不因此被强制终止。故障时保留上一份成功快照，当前实例报告写盘失败，不能宣称最新状态已经保存。

## 存储和备份

Station 使用任务数据库旁的 `<数据库名>-pm-starts.sqlite3`；Worker 使用数据目录的 `worker-pm-starts.sqlite3`。在原启动回执数据库中新增 `pm_checkpoints` 表，每个 PM 保存一份最新的完整快照。进程所有者与递增版本共同防止旧实例或新进程直接覆盖原现场。

完整节点备份包含启动数据库，因此同时保留检查点与启动回执。恢复备份不会自动接管执行；普通新实例不能覆盖原进程的检查点；显式恢复必须取得原路径进程锁，并按检查点版本原子接管。生产环境切换、多机同一时点备份和旧备份之后的外部操作仍需单独处理。

原始快照包含任务输入、输出和上下文，应按任务数据保护。网页核实接口只返回阶段与统计摘要，不返回原始提示词、输入、输出或进程所有者。查询使用只读 SQLite，不创建缺失数据库、表或执行编号。

## 恢复前逐项核实

任务详情新增「核实恢复条件」。Secretary 按持久化 PM 归属查询原节点；原节点读取检查点，按原执行编号查询原执行节点，先核对设备身份，再核对执行编号、PM、任务、执行者和步骤名称。查询仅使用 GET，不派发、不迁移、不分配新编号，不改写检查点或输出。

| 结果 | 含义 |
|---|---|
| 成功输出已保存 | PM 已保存并接受输出，可作为后续恢复依据。 |
| 已取得成功回执 | 原执行返回成功，但尚需 PM 质量检查；不直接写入成功输出。 |
| 原执行仍在等待结果 | 保留原执行编号，不另起一次执行。 |
| 执行结果待核实 | 超时、掉线、回执缺失或本地执行没有持久化结果；不能当成未执行。 |
| 未登记执行请求 | 检查点中没有该步骤的执行请求，后续仍需恢复授权。 |
| 归属不匹配 | 节点或执行身份不符，拒绝采信结果。 |

每次有 8 秒的请求调度预算、单请求至多 2 秒且不重试/不跟随重定向。超出预算时点击「继续核实剩余步骤」，沿用同一检查点版本；版本变化必须从头重新核实。计划最多核实 150 个步骤，分批结果不会单独宣称整个计划已核实完毕。连接读取超时由 HTTP 库控制，此预算不等同强制中止底层网络线程。

原 PM 仍在运行、停止意图、任务终态、超出原时限、已有交付或替代任务都会明确提示。查询期间任务或检查点变化会丢弃过期结果。原始输入和输出不展示在恢复摘要中。

接口：Secretary `GET /api/tasks/{task_id}/recovery-check`；原 PM 节点 `GET /role/pm-recovery/{pm_id}?task_id=...`。可传 `offset` 与 `expected_revision` 继续核实。返回 `steps`、`blockers`、`revision`、`next_offset` 等摘要。`resume_supported` 表示现场格式和状态支持申请恢复，不证明原进程已退出，也不是恢复授权。即使返回 evidence_complete，也只表示本次收集到执行证据。

原执行回执 `GET /tasks/executions/{execution_id}` 现在直接以只读模式访问已有数据库，缺失时返回 404，不再创建空库或目录。

## 显式恢复原任务（iter-54）

1. 恢复原节点的服务连接，打开原任务详情，点击「核实恢复条件」。
2. 对符合条件的现场点击「恢复原任务」并确认。恢复可能继续产生模型和工具费用，使用原任务剩余时限，不重新开始计时。
3. 查看原任务的步骤进度及交付。重复提交同一检查点版本复用同一个请求编号，不重启第二个 PM；响应未确认时先核实，或重试同一请求。

Secretary 的 `POST /api/tasks/{task_id}/resume` 接收 `expected_revision`。在任务库写事务中复核任务/PM归属、停止意图、交付、替代任务和项目预算，并保存 `_pm_resume` 授权；相同版本复用请求，旧授权历史保留，陈旧的恢复申请不会撤销正在执行的有效授权。普通任务保存不能覆盖授权或原 PM 归属。

原节点 `POST /role/resume-pm` 接收任务、PM、设备、请求编号和预期版本。它从原检查点读取秘书地址，向 `/api/tasks/{task_id}/resume-authorization` 核实当前授权；不接受客户端提供的新任务内容或秘书地址。恢复实例在新工具执行、质量检查、聚合及交付前再次检查业务授权与原时限，查询失败停止后续调度。

新版正常启动在执行前取得 `<启动库路径>.process-lock` 操作系统独占锁，并把本机身份与原始绝对路径写入检查点。锁保留到整个进程退出；PM 标记停止或工作线程结束都不释放，因为其他工具线程仍可能运行。恢复必须在同一 Linux 主机、同一数据路径取得该锁，再按版本在同一 SQLite 事务中更换检查点所有者、递增版本并记录恢复请求。旧进程仍存活或同进程旧实例时拒绝接管。锁文件本身不是存活证明，不得通过删除文件强制恢复。

续跑保留原任务、计划、执行编号、成功输出、重试历史、澄清数据和时限。已接受输出直接复用，已收到但尚未接受的成功回报先进入原 PM 质量检查；远端在途执行只按原编号查询并核对节点身份。未执行工作按原依赖继续调度。已保存聚合结果不再次调用聚合模型；已准备或发送的交付请求在秘书尚无交付时沿用原请求内容和时间。已生成单任务结果可继续交付，不重复调用工具。规划前退出可继续原任务规划。

## 当前限制与验证边界

- 只支持带进程排除凭据的新版任务在原 Linux 主机、原路径恢复。旧版现场、跨机迁移、复制/恢复到新目录、Windows 恢复不在本轮支持范围内；旧任务查询能力保留。
- 已暂停、取消、失败、超过原时限、无可验证继续点的澄清、已有交付或替代任务时拒绝直接恢复。已保存交付请继续验收；本轮不提供暂停后的继续按钮。
- 本地/直接执行已经开始但没有持久化返回结果时拒绝重做；即使 PM 进程退出，外部工具或它创建的进程仍可能产生副作用。远端结果未知保持查询，直到得到原回执或原时限耗尽，不另建执行编号。
- 进程锁不替代共享网络文件系统的分布式租约；不要把同一 PM 数据目录克隆到多台主机并同时运行。检查点写入失败仍停止后续调度，不强杀工具。
- 已验证真实 PM 子进程在 A 输出保存后突然退出，新进程复用 A、只执行 B 并交付；Station/Worker 的真实本机 HTTP 链路验证等待原执行回执后继续依赖；Chrome 验证确认、失败重试、重复请求、迟到响应隔离和桌面/手机。
- 测试中的模型与工具结果为模拟数据。真实模型、实际多主机故障、Windows、生产数据恢复切换及 72 小时持续运行仍未验收。

## 等待 Boss 回复时恢复（iter-55）

任务详情的「查看待回复问题」读取原节点已保存的问题、问题编号和回答状态。原 PM 未运行时先核实恢复条件并恢复原任务，再回复；秘书不会离线代存回答。需求细化阶段支持保留原轮次、累计上下文、问题编号及原截止时间。恢复前已保存的回答直接消费，不再次询问；原等待时间耗尽时按超时继续既有流程，不重置总时限。

「保存回复到原任务」或 PM 线程发送固定问题编号。原节点先写检查点再唤醒 PM 和确认；保存失败保留原文。相同问题的相同回复重试仅确认已保存，不重复消费；不同回答或旧题改答拒绝。已消费问题保留历史，因此第一题确认丢失而第二题已出现时，重试仍针对第一题。任务停止/交付后只允许确认已保存的相同回答，不接收新回答；该确认目前需要原 PM 实例仍可访问。

新问题出现而输入框中有旧草稿时，不改绑问题；先复制保存并清空草稿，再点击读取当前问题。线程发送成功会再读取当前题目。旧版客户端及 Telegram 无问题编号按钮需刷新/升级；终止任务使用正式取消入口。

此恢复仅支持具有格式化 refinement 继续点的规划前需求澄清，最多两轮。旧格式、执行期间任意自定义澄清、暂停后继续仍不支持；沿用原 Linux 主机、原路径与进程排除限制。

## 暂停现场与控制回执（iter-56）

检查点新增 `pause`（暂停前阶段、时间及规划/聚合原响应）和 `control_receipt`（原设备/PM/任务/请求/动作与协作停止确认）。重复暂停不覆盖最初继续点；同一停止请求重试不重复写盘；写盘失败仍停止后续调度，但不假报停止确认已持久化。

暂停时直接执行的返回结果沿用原执行编号保存在 `direct_execution`；子任务回报校验原四项身份及步骤名称后保存 `received_result`，不进入 `subtask_outputs`、质量检查或后继调度。首份终态保存后，重复回报不写盘，冲突回报不覆盖。规划与聚合的原响应仅保存为待处理数据，不解释成有效计划或交付物。取消/失败现场不接收此类晚到结果。

原节点查询可从已存检查点返回匹配的控制回执，不把历史回执当作 PM 仍存活或外部工具已退出。恢复状态容器保留停止标志；旧现场缺少新增字段仍可只读查询。本轮没有提供暂停继续的启动操作，原有恢复校验仍拒绝暂停现场。


## 暂停继续与执行代隔离（iter-57）

`pm_activity.py` 追踪主执行、进度循环、调度、质量回调与回复处理的完整调用周期；同一数据库路径和 PM 的所有存活实例均参与退出核实，不能只检查 `running`。核实通过后封闭旧实例的入口，旧 stop_event 不清除；新 PM 使用独立 owner 写入检查点。进程退出场景仍要求原路径 OS 生命周期锁。普通恢复同样检查同进程旧活动，防止继续产生的独立 owner 绕过退出核实。

`task_continue.py` 保存 `_pm_continue`（原暂停编号、预期版本、请求编号、历史及状态）。准备阶段保留暂停；`pm_continue.py` 在原节点用 SQLite 版本比较持久化 `continuation.state=prepared` 并替换 owner，随后秘书复核预算/交付/替代任务/当前暂停，归档 `_pm_control`，设置 `_pm_generation`，清除旧 `_pm_resume` 与待核实标记，事务激活。

新线程先启动并等待闸门；新现场与 `continuation.state=launched` 成功落盘后才放行。准备后崩溃、激活确认丢失、线程创建失败及启动落盘失败可重试同一请求。启动已落盘时重复请求只读确认；此后进程死亡走普通新版恢复，不重置原时限。查询准备现场返回原授权版本，刷新页面仍可复用请求。

新快照字段 `generation`、`continuation` 兼容缺失的旧记录。停止请求带执行代号；原节点拒绝不匹配请求。秘书在数据库事务内核对状态、进度、子任务同步和交付的 generation，旧全任务保存也不能跨代覆盖。原暂停回执核对 generation，第二次暂停确认丢失仍可从磁盘核实。

暂停期间保存的规划/聚合响应复用，原始子任务结果继续走质量与失败分支，未知结果不重试。没有执行编号的预派发标记只在新版暂停继续中清理；执行必须先持久化编号，因此该标记不代表外部操作已发出。已有本地未知编号仍拒绝重做；远端未知沿原编号查询。无中央 schema 变更。
