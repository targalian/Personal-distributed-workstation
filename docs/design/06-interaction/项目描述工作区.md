# 项目描述工作区（存储与接口）

## 范围

本切片只落地「项目描述的存储、版本、审阅、导出与确认下发」，不包含从对话自动生成（LLM）和前端页面；这两块会在下一片按 Yomk 组件服务的方式补。

## 数据模型

一份项目描述由三部分组成，共用同一个文档：

- `sections`：13 个固定章节（背景／目标／用户／范围／需求／质量／方案／数据／里程碑／资源／风险／问题／验收），每章最多 12000 字。
- `nodes`：模块／功能／讨论节点，最多 150 个，支持三层嵌套（`parent_id`）。
- `edges`：执行依赖边，最多 500 条，必须是 DAG，不能自连或重复。

`ProjectBrief` 用 Pydantic v2 `model_validator` 校验：章节白名单、节点 ID 唯一、父子成环、嵌套深度、依赖边引用与环检测。渲染成 Markdown 时 Mermaid 的节点 ID 自动生成、标签转义，用户内容不能截断代码块。

## 存储

`BriefStore(root)` 把每个对话写成 `<root>/project_briefs/<conv_id>/brief.json`：

- `revision`：单调递增；`save` 必须带 `expected_revision`，不一致抛 `RevisionConflict`。
- 每次提交把旧版本快照写到 `revisions/`，`history` 只列已提交版本，`revision` 读指定版本，`restore` 把旧内容作为新 revision 写回，历史不丢。
- `proposal`：AI 建议（本切片可由接口写入，生成在下一切片），审阅时按字段选择采纳；结构变更（节点/边）作为一个整体项。
- 所有写入先写临时文件再原子替换，进程中断不会留下半截文档。

## HTTP 接口

前缀 `/api/conversations/{conv_id}/brief`，需要 Secretary 已激活且对话存在：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `` | 读当前文档（含 revision、markdown、proposal） |
| PUT | `` | 保存文档（`document` + `expected_revision`），冲突 409 |
| GET | `/markdown` | 导出 `项目描述.md` |
| POST | `/review` | 审阅建议（`proposal_id`、`expected_revision`、`selected`） |
| GET | `/history` | 已提交版本列表（支持 `before_revision` 分页） |
| GET | `/history/{revision}` | 某版本内容 + 与当前的差异 |
| POST | `/history/{revision}/restore` | 把旧版本恢复为新 revision |
| GET | `/readiness` | 缺项与确认状态（advisory，不代表质量达标） |
| GET | `/handoffs`、`GET /handoffs/{revision}` | 下发记录 |
| POST | `/handoffs` | 确认下发：每个已保存版本只下发一次，先落记录再建任务 |

## 下发语义

`POST /handoffs` 先写 `<revision>.json` 记录（含内容摘要 sha256）再调 `submit_task_from_chat`：

- 同一 revision 重复下发直接返回已有记录，不重复建任务。
- 调用失败或超时记为 `uncertain` 并保留记录，**不自动重试**——可能任务已建。
- 下发只带已保存文档，不含待审阅建议。

## 验证

`tests/test_project_brief.py` 覆盖：Markdown 章节与嵌套图、非法图被拒（重复 ID／环／悬空边／四层嵌套）、保存与版本冲突、建议审阅与按字段采纳、历史与恢复、路由的 404/409/503 与导出、下发幂等与超时记 `uncertain`。

未覆盖：从对话生成（LLM）、前端页面、多机并发写同一对话目录。
