# Boss 与秘书：项目描述工作区

## 项目背景与当前架构

本项目的主要产品是 `lan_mesh` 下的 Python/FastAPI 分布式工作站，Web 控制台由 `dashboard.html` 提供。`quicklan-main` 是独立的 Tauri/React 局域网文件分享子项目，本次交互改动落在工作站 Web 控制台。

原流程：Boss 发消息 → Secretary 调用模型并识别关键词 → 创建任务 → PM 分解并分配 Worker → 汇总交付。已有 L1 项目对话、L2 PM 线程、共享文件夹中的会话记录，以及 PM 执行 DAG。原 DAG 面板支持演示性的拖动，但保存已停用，不能承担需求共创。

原流程的两个问题：聊天没有稳定的需求产物；「帮我做一个」等讨论语句会立即触发提交任务。

## 目标与成功指标

- 每个会话维护一份项目描述，聊天、章节编辑和需求图共用内容。
- 导出名称固定为 `项目描述.md`，离开工作站后仍能阅读与评审；支持 Mermaid 的 Markdown 阅读器可显示依赖图。
- 支持三层包含关系（模块 → 功能 → 子功能），任何编辑均不得保存循环依赖、重复边、悬空父节点或第四层。
- 页面切换保留未保存草稿；保存失败、模型输出无效和版本冲突不覆盖原稿。
- 明确下发指令后，把完整 Markdown 作为任务描述交给现有 PM 流程。

## 文档内容约定

| 内容 | 要回答的问题 |
| --- | --- |
| 项目背景与问题 | 为什么要做，现有流程的痛点是什么？ |
| 目标与成功指标 | 预期结果、基线、可测量指标是什么？ |
| 用户角色与场景 | 谁在什么情况下使用？ |
| 范围与非目标 | 本期做什么，明确排除什么？ |
| 项目需求与优先级 | 哪些是 P0/P1/P2，为什么？ |
| 非功能需求 | 性能、安全、可靠性、可用性、兼容性有什么要求？ |
| 解决方案与备选方案 | 采用哪种方案，有什么成本和取舍？ |
| 数据、接口与依赖 | 输入输出、外部系统、权限、数据归属是什么？ |
| 里程碑与交付物 | 分几期，各期输出什么？ |
| 预算、资源与约束 | 人员、模型、算力、成本和时间边界是什么？ |
| 风险与假设 | 哪些假设尚未验证，有何应对方式？ |
| 功能待讨论项与决策记录 | 问题、影响、候选方案、负责人、结论是什么？ |
| 验收标准与验证方式 | 谁通过什么测试判断需求完成？ |
| 模块与功能分解 | 层次、说明、优先级、确认状态、负责人和验收点是什么？ |
| 依赖 DAG | 谁依赖谁，哪些工作可以并行？ |

未知信息保留「待讨论」，AI 建议标为「建议」，只有 Boss 明确确认的内容才标「已确认」。确认状态是需求确认程度，不是任务运行状态。

## 用户操作

1. 在秘书对话中讨论项目，右侧展示「项目描述.md」。秘书通过结构化输出生成待审阅建议；在「AI 建议」比较当前内容和建议，勾选修改后点击「保存所选，忽略其余」。模型未按协议返回时仍显示普通回复，可使用「从对话整理」重试。
2. 在「文档」视图编辑章节，切换到「需求 DAG」补充模块、功能、验收标准。
3. 拖动节点调整位置；父框带着子节点移动。选中框后添加子节点，或在「所属框」选择父节点。支持双击折叠、缩放、平移、自动布局、适配和撤销／重做。
4. 点击「依赖连线」，依次选前置节点和后续节点。选中连线后可删除；祖先与后代的包含关系不能再作为依赖。
5. 保存后刷新可恢复内容、坐标和折叠状态。导出包含章节、嵌套功能清单与 Mermaid 图。Markdown 预览显示源码；不提供任意 Markdown 反向解析导入。
6. 输入「下发项目描述」将已保存的完整描述交给 PM；项目讨论本身不会触发任务提交。原有明确的「提交任务：…」入口继续可用。

「从对话整理」也只生成建议。建议默认不勾选，可逐项选择项目名称、章节或节点属性；新增／删除节点、嵌套、节点顺序或依赖变化合并为一个结构项，整体采纳以保持 DAG 完整。采纳会一次保存所选修改、忽略未选修改并增加版本；忽略全部不增加版本。若模型输出与文档一致，不创建建议。

「版本历史」列出手工保存、AI 采纳和恢复记录，含版本、时间、来源与标题，每页 50 条，可加载更早版本。选择一项后点「查看版本与差异」，比较当前已保存内容与该历史版本，也可查看历史 Markdown。「恢复所看版本为新版本」需确认，创建递增版本而不覆盖旧快照；本地未保存修改时禁用，服务端再次验证当前版本。恢复后已有 AI 建议可能过期，需忽略后重新整理。

旧格式数据升级后只能保存升级时的最新文档及之后的版本，无法还原此前未记录的历史。浏览器 50 步撤销和服务端历史是两个机制：前者刷新后清空，后者刷新／重启后保留。

每个会话最多一份待审阅建议，刷新或服务重启后仍保留；已有建议时先处理，再重新整理。生成期间发生版本变化会拒绝保存建议。建议生成后若手工保存了新版本，建议变为过期，只能忽略后重新整理；采纳接口同时检查文档版本和建议 ID。存在未保存草稿时禁用采纳，忽略建议保留该草稿。待审阅建议不会进入 Markdown 导出或 PM 下发。采纳在浏览器历史中记为一步，撤销后仍需手工保存。

顶部「撤销／重做」在文档、需求 DAG 和预览视图共用，保留当前会话最近 50 步修改。文档标题和章节的连续输入（间隔不超过 1 秒且未离开字段）合并为一步；拖动父框、删除子树、编辑节点和依赖各为一步。没有实际变化的操作不会占用历史或清空重做。

在项目描述区域使用 Ctrl/Cmd+Z 撤销，Ctrl/Cmd+Shift+Z 或 Ctrl+Y 重做。节点属性文本框尚未提交时保留浏览器原生文本撤销，离开字段后纳入文档历史。快捷键不接管聊天输入框。撤销时保留文档字段焦点和展开章节，DAG 节点仍存在时保留键盘焦点。

保存不会清空历史；保存后撤销只修改本地草稿，需再次保存才能更新服务端。恢复到最后保存的内容会显示「已同步」，并保留当前服务端版本号。会话间历史隔离，同一版本会话往返保留历史。显式重新加载、页面刷新或接受 AI／其他页面的新版本时清空旧历史，避免旧快照覆盖新内容；版本冲突时保留草稿及历史。这是浏览器会话内编辑历史，不是持久化版本回滚。

发送聊天前，界面会先保存手工修改，确保秘书看到最新内容。跨页面并发修改会返回 409，并保留当前草稿；可先导出草稿再加载服务端版本手工合并。浏览器关闭前会对未保存修改给出提示。

## 数据与模块

- `project_brief.py`：Pydantic 数据模型、三层包含与 DAG 校验、会话隔离存储、版本比较、Markdown 输出和模型输出协议。
- `brief_review.py`：字段差异生成、结构变更分组、所选变更合并与完整文档复验。
- `chat_handler.py`：向秘书注入当前项目描述，解析结构化回复并保存；显式整理与下发完整文档。
- `station_routes_briefs.py`：读取、保存、模型整理与 Markdown 下载接口。
- `web/static/project-brief.js` / `.css`：独立的文档与 SVG 框图编辑器，无新增线上 CDN 或前端构建依赖。
- `role_cards.py`：秘书以澄清需求、沉淀产物为先的角色约束。

结构化数据是单一事实源：`conversations/project_briefs/<conv_id>/brief.json`。文档与可选 `proposal`（ID、基准版本、时间、候选文档、差异）放在同一文件，经原子替换保存；旧文件缺 proposal 时按无建议读取。Markdown 仅从已保存 document 生成。底层沿用共享目录，没有共享目录时沿用 `~/.lan_mesh/conversations`。不改写 PM 运行中的任务 DAG。

版本快照写入同目录 `revisions/<revision>-<随机标识>.json`，快照包含完整 document、时间及来源，历史记录通过主文件内部 `_history` 索引发布。写入先准备独立快照，再原子替换主文件；失败时旧主文件及历史索引不变，未被索引引用的准备文件不可通过 API 读取。此类孤立文件可能残留，暂不自动清理或设置历史保留期限，备份需覆盖整个会话目录。单进程锁假设不变，历史不是防管理员篡改的审计存储；来源标识为操作类型，尚未绑定多用户身份。

包含关系使用 `parent_id`；依赖关系使用 `edges`；节点坐标相对父框。最大 150 节点、500 条边、三层嵌套。版本号防止旧页面覆盖新版本；同一 Secretary 内使用锁串行写入。

| API | 用途 |
| --- | --- |
| `GET /api/conversations/{id}/brief` | 当前描述、版本、章节标签、Markdown、可选 proposal |
| `PUT /api/conversations/{id}/brief` | 提交 `document` 与 `expected_revision` |
| `POST /api/conversations/{id}/brief/generate` | 按当前描述与最近对话生成待审阅建议，携带 `expected_revision`；不增加文档版本 |
| `POST /api/conversations/{id}/brief/review` | 携带 `proposal_id`、`expected_revision`、`selected` 变更 ID 列表；空列表表示忽略全部 |
| `GET /api/conversations/{id}/brief/markdown` | 下载 `项目描述.md` |
| `GET /api/conversations/{id}/brief/history` | 最近 50 条历史元数据，返回 next_before；用 before_revision 加载更早记录 |
| `GET /api/conversations/{id}/brief/history/{revision}` | 历史文档、Markdown 及与 current_revision 的差异 |
| `POST /api/conversations/{id}/brief/history/{revision}/restore` | 携带 expected_revision，恢复为递增的新版本 |

不存在的对话返回 404，秘书未激活返回 503，结构错误返回 422，旧版本写入返回 409。现有工作站认证中间件覆盖这些 API。

## 方案比较

| 方案 | 适配性与取舍 |
| --- | --- |
| 原生 SVG + 结构化章节（本期） | 适合现有无构建的 Web 控制台；部署依赖少，能够完成三层包含、依赖与持久化。复杂路由、多人协作需后续扩展。 |
| React Flow + ELK | 适合未来将整个工作台迁移至组件架构时采用；多选、端口、自动分层布局更成熟，但引入 React 构建和迁移成本。 |
| Markdown + Mermaid 源码 | 适合导出和版本评审，单独使用无法提供完善的拖动与结构化编辑。 |
| 纯自由白板 | 自由度高，但难以约束 DAG 和稳定地产生可执行需求，不适合作为唯一事实源。 |

## 后续优化优先级

| 优先级 | 建议 | 用户收益／待决策点 |
| --- | --- | --- |
| P0 | AI 字段锁定与建议合并 | 差异预览和逐项采纳已完成；后续可锁定不可改写字段，支持旧建议与新手工编辑三方合并。 |
| P0 | 不可变确认版本与 PM 下发记录 | 当前下发完整 Markdown；进一步绑定需求版本、任务 ID 和验收，提供追溯。 |
| P0 | 待讨论事项独立队列 | 结构化记录问题、选项、责任人、截止时间、是否阻塞；一次只询问最关键的 1–3 个问题。 |
| P1 | 历史归档与作者身份 | 已支持持久化快照、版本比较和恢复；后续增加身份归属、归档策略与跨进程写入仲裁。 |
| P1 | 完整性评分 | 展示缺少验收点、无负责人、未确认依赖等实际缺项；不以字数充当质量指标。 |
| P1 | 需求节点 ↔ 对话证据 ↔ 执行任务映射 | 点节点可看到来源讨论、关联 PM 任务和最终验收产物。 |
| P1 | 对话流式返回与长请求后台化 | 目前沿用同步模型调用；长文档可能触及聊天 60 秒超时，应引入作业 ID 和流式进度。 |
| P2 | 节点搜索、多选、边路由优化、缩略图 | 大型图减少视觉遮挡与操作成本；超出 150 节点时优先考虑分项目。 |
| P2 | 可靠跨主机协作锁／CRDT | 当前遵循单个活跃 Secretary 写入；文件锁不跨进程，真正多写入者需要存储层仲裁。 |

## 边界与待讨论项

- 文档粒度当前为会话：一个会话一份描述。多个会话是否汇总到同一个项目，需要明确产品规则。
- 生成上下文沿用聊天最近 20 条消息，并附上完整当前文档；历史尚未沉淀的信息可能遗漏。可进一步增加分段汇总和消息来源链接。
- 自动布局按同级依赖顺序纵向排列，并不提供复杂的避障连线路由。
- 模型结构化协议依赖供应商输出质量：错误输出不落盘，原稿保留；尚未使用供应商专属 JSON Schema 强约束接口。
- Markdown 可携带可渲染的 Mermaid 图；交互坐标和折叠状态由工作站 JSON 保存，不作为独立 Markdown 的交互能力。
- 需求确认后如何冻结、谁有确认权、未决问题能否阻塞执行、预算是否必填，仍需进一步定义。
