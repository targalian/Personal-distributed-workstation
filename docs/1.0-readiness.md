# 1.0 可用性门槛

评估日期：2026-10-15，第 54 轮。定位为受控试用。版本号不代表完成百分比；发布依据是验收证据。

## 建议发布范围

个人或小团队、可信局域网、1–3 台工作站，完成「讨论需求 → 审阅并确认项目描述 → PM 执行 → 交付验收」。公网、多租户、手机 App 和大规模调度不作为本次 1.0 的默认范围；若扩大范围，应先增加相应权限和部署验收。

## 距离可投入使用的 1.0

项目描述工作区已具备结构化章节、Markdown 导出、三层嵌套 DAG 编辑、撤销、版本历史、AI 建议审阅及确认版本下发，可在有人看护的条件下试用。当前证据不足以支持无人值守地承担重要任务；主要差距集中在执行可靠性和实机验收。

| 缺口 | 用户实际会遇到的问题 | 关闭缺口所需证据 |
|---|---|---|
| PM 重启后的安全续跑 | 新版任务已支持原 Linux 主机原路径的显式接管和续跑；本地未知执行、暂停/待澄清及旧版任务仍受限 | 已有真实进程退出及本机 HTTP 证据；继续实机多节点故障验收，完善暂停/澄清恢复及工具副作用处理 |
| 真实模型到交付的完整链路 | 模拟测试不能证明模型能正确整理需求、调用工具并交付可用文件 | 文档、代码修改、跨机任务三类真实案例，保存确认版本、实际产物、验收结果和成本 |
| 多机故障与停止/预算控制 | 网络中断可能留下待核实状态；PM 停止不等于在途工具或付费请求已停止 | 两台以上实际主机的断网、掉线、重启、重复请求、取消和预算边界演练；核对外部副作用与账单 |
| 数据与发布可维护性 | 本机启动正常不等于新用户可安装，也不等于升级失败能恢复 | 干净环境安装、依赖版本验证、旧数据迁移、升级回退、备份恢复切换及关键回归自动阻断发布 |
| 长期运行与操作闭环 | 还缺少长期资源使用和陌生用户独立完成任务的证据 | 至少 72 小时实机持续运行；新用户按说明完成配置、任务、产物定位及故障处理 |

建议按三个里程碑推进：基于已实现的有条件 PM 续跑补齐停止/澄清边界，再完成真实模型和多机故障验收，最后完成安装升级、备份切换和 72 小时发布候选验证。72 小时本身是最低观测窗口，不能用开发轮数或单测数量推算发布日期。

交互上优先补长请求的流式进度/后台作业，减少同步聊天 60 秒超时；再补待讨论项队列、确认前缺项提示及需求节点到任务/产物的直接导航。字段锁定、建议三方合并、大图搜索和复杂布局可以后续迭代。当前每个会话一份描述，多会话汇总到同一项目的规则仍需明确；导出的 Markdown 可阅读并包含 Mermaid，拖动与嵌套编辑在工作站内完成。

## Loop 顺序

1. 数据闭环已具备修订历史、确认版本与任务绑定；继续以真实执行验证追溯完整性。
2. 真实任务与故障验证：优先修复验证暴露的问题，不靠扩展 UI 替代可用性验证。
3. 发布候选：可复现依赖、安装升级恢复、自动回归与持续运行。

依赖实际主机、有效模型配置和付费调用额度的验证，应明确记录环境条件和授权范围。缺少条件时标为未验证，不宣称通过。持续开发可以推进独立任务，但不得把发布检查表全部完成作为既定事实。
