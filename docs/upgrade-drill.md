# 旧版源码升级和回退演练

`scripts/upgrade_drill.py` 在临时源码和数据目录运行两个版本的真实启动器，验证实际 HTTP 行为，并在拒绝启动后从完整离线归档恢复。默认基线固定为已发布 v0.34.18 的提交 `2141a62b1d54d068981ca76988e683f82f07313b`；候选为当前工作区。

## 执行

使用 [发布检查环境](release-checks.md) 的 Linux / Python 3.10 虚拟环境：

```bash
env -u PYTHONPATH -u PYTHONHOME .venv-release/bin/python scripts/upgrade_drill.py \
  --venv .venv-release --output /tmp/workstation-upgrade-001
```

输出目录必须不存在。基线提交必须在本地 git 历史中；浅克隆需先取得相应历史，脚本不会自动联网拉取。CI 使用完整历史。`--baseline-ref` 可以选择可信的本地祖先提交；它必须支持 `LAN_MESH_DATA_DIR` 并提供运行依赖锁，不支持通过修改 HOME 运行更早版本。

两个源码版本分别校验虚拟环境、Python 3.10、精确运行锁、pip 依赖一致性、该版 requirements 范围和依赖导入。默认共用传入环境；基线依赖不同时，先按基线锁安装另一个环境，再传 `--baseline-venv /绝对路径/旧版环境`。本脚本不负责安装或升级这些环境。共用环境通过仅表示同时满足所选两版的锁，不代表不同依赖组合也已验收。

## 检查顺序

1. 从固定提交导出应用源码，并复制当前候选源码；记录提交、dirty 状态、两边解释器和依赖锁摘要。拒绝源码符号链接，排除个人模型池、资源文件和 `.env`。
2. 用旧版代码准备合成数据：两版项目描述、三层节点、待审阅建议、确认版本与已验收任务，以及已完成/结果未知的执行回执和 Markdown 产物。它们是验收夹具，不是模型生成成果。
3. 通过旧版真实启动器启动 Station、激活 Secretary，经 HTTP 核实版本、身份、项目描述/历史/建议、任务验收及回执状态；停止后核实执行编号不能重新申领。
4. 使用旧版备份 CLI 创建并校验完整离线归档。
5. 使用候选启动器打开相同数据路径，再次核实原数据、文件 SHA-256 和身份；保存一个新的需求修订，并核实旧回执去重。
6. 在临时试运行主库注入不支持的 schema v999。候选必须非零退出且明确拒绝此版本，HTTP 端口关闭；拒绝前后的数据库逻辑内容摘要相同。
7. 使用候选备份 CLI 将归档恢复到新目录；保留试运行目录，将恢复数据放回原路径；用旧版代码和旧版环境启动，核实原修订、待审阅建议、身份、验收、回执去重和产物摘要。试改稿不会混入回退数据。

每次启动均有独立进程组，退出时清理子进程并检查端口释放。停止超时会强制清理，但该阶段仍判失败，不能以强制退出替代正常关闭验收。子进程只继承 OS 基本变量，不继承环境中的模型密钥、云/Bot/资源配置和额外 API 认证设置；使用空模型池和独立 UDP 端口，关闭自动升级。不修改日常工作站数据，也不调用模型或外部工具执行任务。

## 证据

输出目录包含 `upgrade.json`、各阶段日志、`fixture.json` 及合成数据的 `before-upgrade.zip`。报告保留固定基线提交、候选提交/dirty 标记、运行时和锁摘要、HTTP 版本、节点身份、每个完成阶段、当前阶段和错误。失败或中断不能标为通过；旧报告不能覆盖。临时运行目录会清理，日志和合成归档留在指定输出目录。

完整 `release_check.py` 将本演练作为第六项门禁，失败会使发布检查失败。GitHub Actions 上传同一证据目录；EN 强制分支保护仍需单独配置。

此检查验证指定 Linux 源码及依赖组合的单机切换，不代表所有历史版本、Windows、物理多节点、生产切换或 72 小时稳定性。v0.34.18 和本轮候选的主库 schema 均为 v5；历史 schema 的升级、SQL 故障和事务回滚另由 [数据库升级专项](schema-upgrades.md) 覆盖。v999 是人为注入的启动拒绝场景，不能作为真实迁移失败的替代证据。
