# 数据库升级、快照与回退

从 v0.41.14 起，Station 主库在修改 schema 前建立恢复快照，并把建表、所有待应用迁移和版本号写入放在同一个 SQLite 事务里。该机制补充整机备份，不能替代它。

## 启动时的行为

1. 用 `BEGIN IMMEDIATE` 取写保留锁，读取现有 schema 版本。
2. 库版本高于当前程序支持版本、版本内容无效，或待应用迁移缺函数时，直接拒绝启动，不改写库；不会悄悄提高版本号。
3. 已有库需要迁移时，先用独立只读连接 + SQLite backup API 保存已提交数据（含 WAL 中已提交页面）。快照先写 `.pending`，通过 `integrity_check` 和文件同步后才独占发布为 `.sqlite3`；之后才开始 schema 写入。崩溃遗留的 `.pending` 不能当正式备份用。
4. 逐条执行建表与迁移 SQL，不用会隐式提交事务的 `executescript`。已有列跳过，其他 SQL 错误向上传递。
5. 全部成功才提交；失败回滚整次初始化、关闭连接并让启动失败。

新空库与当前版本库不产生迁移前快照；原有「启动后日常快照」保留，但不能当作升级前备份。

快照位置：`~/.lan_mesh/backups/upgrades/`。文件名含原库名、原路径摘要、源/目标版本与随机后缀；Unix 权限 600。快照不受日常保留三份的清理规则影响，也不会覆盖同名快照，容量需自行管理。备份失败会阻止迁移。

## 升级操作

- 停掉参与节点和外部写入，核实在途任务与副作用。
- 先做整机离线备份（见整机备份说明），保留原代码与依赖锁。
- 更新代码、按目标版本安装依赖，启动后核对健康、会话、任务归属与交付。
- 检查通过后再恢复提交业务任务。

## 失败与回退

迁移失败时先看错误和迁移前快照路径。事务回滚应保留原数据，但要做 schema 版本与 `PRAGMA integrity_check` 复核。不要手工改版本号，也不要删去重数据后用旧代码强行打开新 schema。

完整回退用同批离线备份 + 匹配的代码版本：先恢复到新目录验证，再停服务、保留当前目录、把恢复数据放回原路径。避免混用旧 WAL/SHM 与不同备份批次的数据。

单库迁移前快照只保护主库 schema 变更前的状态，不含独立回执库、会话文件和外部工具数据。服务已产生新任务时，应走整机备份的统一切换流程。恢复较早备份不会撤销外部工具已经发生的副作用。

## 验证范围

`tests/test_database_upgrade.py` 覆盖：v4→v18 升级前快照、快照内容与升级前逐行一致、迁移后段失败回滚（DDL/数据/版本都不变）、缺失迁移中止、库版本高于程序被拒、快照失败不写库、新空库不产生快照。

未覆盖：跨历史版本的升降级兼容、物理多节点同时恢复、Windows 之外的生产切换演练。
