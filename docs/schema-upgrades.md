# 数据库升级、恢复与回退

从 v0.34.19 起，Station 主库在修改 schema 前建立恢复快照，并将本次建表、所有待应用迁移和版本号写入放在同一 SQLite 事务中。此机制补充完整离线备份，不能代替它。

## 启动时的行为

1. 获取 SQLite `BEGIN IMMEDIATE` 写入保留锁，读取现有 schema 版本。
2. 如果库版本高于当前程序支持版本，或版本内容无效，直接拒绝启动，不改写库。缺失迁移函数也必须失败，不能只提高版本号。
3. 已有数据库需要迁移时，先通过独立只读连接和 SQLite backup API 保存已提交数据，包含 WAL 中已提交页面。快照先写入 `.pending`，通过 integrity_check 和文件同步后才独占发布为 `.sqlite3` 并同步目录；此后才开始 schema 写入。崩溃遗留的 `.pending` 不能作为正式备份使用。
4. 逐条执行建表与迁移 SQL，不使用会隐式提交事务的 executescript。已有列可以跳过，其他 SQL 错误必须向上传递。
5. 全部成功才提交；失败回滚整次初始化，关闭失败连接并让启动失败。进程突然退出由 SQLite 日志恢复未提交事务。

新空库和当前版本库不产生迁移前快照。原有启动后日常快照仍保留，但不能把它当作升级前备份。

快照位置：`LAN_MESH_DATA_DIR/backups/upgrades/`，未指定时为 `~/.lan_mesh/backups/upgrades/`。文件名包含原库名称、原路径摘要、源/目标 schema 版本和随机后缀；Unix 文件权限为 600。快照不被日常保留三份备份的清理规则删除，也不会覆盖同名快照；需在确认升级和回退窗口结束后自行管理容量。备份失败会阻止迁移，不能忽略错误继续启动。大库需要额外磁盘空间和复制时间，期间其他写入会等待或超时。

## 升级操作

- 停止参与节点和外部工具写入，核实在途任务与副作用。
- 按 [备份说明](backup-restore.md) 创建并校验包含主库、回执、身份、配置和共享目录的完整离线归档；保留原代码版本和依赖锁。
- 更新代码并按目标版本的依赖说明安装。启动后检查健康、会话、需求修订、任务归属、交付验收和执行回执。
- 只有这些检查通过后，才重新开始提交业务任务。

## 失败与回退

迁移失败时，先查看错误和迁移前快照路径。事务回滚应保留原数据，但仍应核实 schema 版本和 SQLite 完整性。不要手工提高版本号，也不要删除去重回执或用旧代码强行打开新 schema。

完整切换回退使用同一批次离线归档和匹配代码版本。先恢复到新目录并验证，再停止服务，把当前目录完整保留，将恢复数据放回原路径；避免混用旧 WAL/SHM、不同备份批次的主库与回执。保留试运行目录可以调查问题，也避免覆盖试运行产生的数据。

迁移前单库快照只保护主库 schema 变更前的状态；它不包含独立回执库、会话文件和外部工具数据。仅在确认这些数据未发生新的业务写入时，才可按原库路径核对单库恢复方案。服务已运行并产生新任务时，应使用完整备份及统一切换流程。恢复较早备份不会撤销外部工具已经发生的副作用。

## 本轮验证范围

`tests/test_database_upgrade.py` 覆盖无版本元数据的代表性旧结构到 v5、v4→v5、快照失败/发布前进程退出、迁移后段失败、缺失迁移、新于程序的 schema、普通日志/WAL 模式下进程突然退出、WAL 已提交内容及并发初始化。

真实本机 Station 演练在临时源码/数据目录进行：启动并升级旧库 → 创建项目描述两次修订 → 停止 → 完整离线归档 → 恢复到原路径 → 再启动核实身份/验收任务/历史 → 试改稿 → 停止 → 放回保留的原目录 → 再启动核实原修订。未调用模型，没有替换用户生产数据。

这证明了指定旧结构和本机恢复流程，不等同所有历史版本二进制与依赖之间的升降级兼容、物理多节点同时恢复、Windows 或真实生产切换。上述项目仍需独立验收。
