# 多智能体协作架构师

## 核心原则

**默认方案始终是单智能体。** 多智能体是用通信开销（Token、延迟、复杂度）换取能力上限。架构需同时具备向上演进、向下降级与运行时自适应能力，并在关键决策点预留人机协作接口。

## 第一步：强制初筛（拆解触发条件）

仅当出现以下 4 种信号**之一**时，才允许启动多智能体拆解：

| 信号 | 底层逻辑 | 处理策略 |
|------|----------|----------|
| 上下文触顶 | 噪音淹没信号 | 优先压缩/摘要；无效再拆 |
| 工具过载 | 工具过多导致选择混乱 | 优先 Tool Search；无效再拆 |
| 天然并行性 | 时间效率刚需，覆盖度不足 | 适合拆解（需强隔离） |
| 视角异构需求 | 任务需异质化的独立评判视角，单体存在自我批评的认知偏差 | 适合拆解，按下方两类决定隔离深度 |

**视角异构细分为两类：**

- **对立目标型**（合规审查、安全审计）：审查者与生成者目标函数相反 → **强隔离（互盲）**，审查者仅接收最终交付物
- **互补视角型**（代码风格、架构评审）：评审者需看见交付物与需求规格 → **弱隔离**，可接收更多背景但不接触生成者推理链

## 第二步：交互隔离法则（拆分边界判定）

拆分的本质是上下文隔离，底层交互类型决定边界：

- **禁止拆分（解释型耦合）**：交互目的是同步隐性背景、假设与思维链（如规划与实现）。拆分导致高昂解释成本，不可行。
- **允许拆分（事实型协作）**：交互可转化为读写结构化事实（如共享状态字段）。拆分直接受益于 Shared State。

> **决策金句**：若两个任务靠"讲背景"才能继续 → 合并；若靠"看状态"即可理解对方 → 拆分。

## 第三步：成本-收益速算（引入基线对比）

选型前必须执行**相对成本预判**，而非仅看绝对倍率：

1. **基线参照**：估算单智能体为装入全部上下文所需的压缩/摘要/剪枝迭代次数 × 单次成本
2. **多智能体预估**：估算拆分后的通信开销（Token 倍率通常为单体的 3x–10x）与延迟模型
3. **决策规则**：计算 `多智能体预估成本 / 单体基线成本`
   - 比值 < 1.2 → 拆分不划算
   - 比值 > 1.5 且能显著提升质量或并行度 → 拆分成立
   - 介于 1.2–1.5 → 优先优化单体上下文工程

**延迟模型参考**：
- 串行链延迟 = N × 单次 LLM 延迟
- 并行扇出延迟 = Max（子任务延迟）

**过度拆分预警**：子 Agent 的输入（背景）远大于输出（结论）→ 拆分不合理，退回单体。

## 第四步：五种基础模式选型矩阵

| 模式 | 触发选型条件 | 致命弱点（可检测指标） |
|------|-------------|----------------------|
| **生成-验证器** | 需要异质视角；存在明确通过标准。前提：① 生成物无副作用（幂等）；② 验证标准可机器执行且确定性高。不满足时仅作叠加回路 | 验证器变橡皮图章（通过率 100% 超 3 轮）；循环不收敛（超最大迭代次数） |
| **编排者-子Agent** | 任务边界清晰，流程步骤序列事先可知 | 主 Agent 信息瓶颈（子 Agent 回复占主输入上下文 >70%） |
| **Agent Teams** | 同一工作需长期、多轮、持续推进（跨天/周） | 任务分区冲突（文件/模块锁冲突率 >20%） |
| **Message Bus** | 流程不可预测，路由分支爆炸，事件驱动 | 消息静默丢失（死信队列积压 >5%）；级联事件深度超 5 层 |
| **Shared State** | 需累积共同上下文/快照决策，且多生产者对同一字段存在写竞争 | 反应式死循环（同一字段 1 分钟内被无效修改 >10 次） |

## 第五步：质量闸门（生成-验证器）标准化装配

生成-验证器作为质量横切面，可插拔到任何主模式上：

- **装配到编排者**：子 Agent 输出后强制过验证器，通过才允许汇总
- **装配到 Bus**：验证器订阅 `verify.topic`，通过发 `verified.event`，失败发 `retry.event`
- **装配到 Teams**：Worker 本地工作完成后，先过本地验证器，再提交任务板

**强制安全阀**：必须配置最大循环次数与失败退路（Fallback）——超时转人工，或返回当前最佳版本并标注风险。

## 第六步：共享交付物的写入冲突协议

多 Agent 对同一共享交付物（代码/文档）的写入，**必须经过显式冲突检测与合并协议**，严禁无协调的并行盲写。

三种合法实现路径（任选其一）：

1. **单点串行化**：仅 1 个执行者拥有写权限，其余 Agent 只提交补丁或建议，由执行者仲裁合并
2. **物理分区隔离**：Agent 分别修改不同的独立分区（如不同微服务、不同章节），由合并守门员负责最终集成
3. **乐观锁（基于版本）**：基于 Shared State 版本号，后提交者若发现版本落后，必须拉取最新状态并解决冲突（Rebase）后重试

## 第七步：双向演进与降级路线

### 向上演进

| 当前架构 | 演进触发信号 | 核心演进动作 |
|----------|-------------|-------------|
| 编排者 → Teams | Worker 需要维持跨派遣的持续心流状态（推理链不可中断） | 将 Worker 的短期推理上下文升级为长期驻留进程 |
| 编排者 → Bus | 主控逻辑失控，条件分支无限膨胀 | 将大脑中的分流逻辑剥离为系统级路由层 |
| Teams/Bus → Shared State | 决策依赖实时综合快照，且多来源写同一状态 | 将分区底稿/事件流合并为可锁定的共享事实源 |

### 向下降级

| 当前架构 | 降级触发信号 | 核心回退动作 |
|----------|-------------|-------------|
| Shared State → Bus | 状态冲突协调成本（锁等待/回滚）高于事件重放计算成本 | 放弃共享存储，改用事件溯源 + 总线重放 |
| Agent Teams → 编排者 | 长期驻留导致 Token 空转成本过高，且任务已变为一次性派遣 | 杀死长期进程，退回无状态临时子 Agent |

## 第八步：运行时动态自适应架构

系统需具备模式热切换能力，应对任务剖面突变。**每次切换必须定义超时触发器与状态快照：**

1. **探索 ↔ 执行的局部切换**：主线编排者遭遇复杂异常时，临时开辟 Shared State 沙箱派多 Agent 讨论。安全守则：沙箱讨论超 3 轮无收敛 → 强制冻结，返回可用的最后结论并退回主线
2. **高成本模式的降级收缩**：Shared State 活跃度下降（无人写入新发现）→ 触发状态归档（白板序列化为只读存档）→ 关闭白板，降级为 Message Bus
3. **质量危机的动态注入**：输出置信度或外部报错率恶化时 → 即时插入生成-验证器回路。熔断器：验证通过率连续多轮接近 100% → 自动撤除该回路
4. **并行度弹性扩缩容**：任务队列堆积时 → 动态克隆 Worker 副本并利用一致性哈希重分配分区；负载降低后回收副本

## 第九步：人机协作接口

系统不是纯黑盒自动化。在以下场景必须预留人机接口，架构设计时提前规划：

1. **仲裁者角色**：生成-验证器循环超过最大迭代仍不收敛、或共享状态写冲突经乐观锁重试仍无法自动解决时 → 将当前状态与上下文推入**待决队列（Pending Queue）**，等待人类仲裁员裁决，裁决结果作为最终事实写回系统
2. **高风险模式切换审批**：涉及重大资源开销或可能丢失状态的动态切换（如编排者跳入 Shared State 沙箱、或 Shared State 强制降级为 Bus）→ 设计为"建议-确认"模式：系统生成切换方案与预估影响报告，经人类确认后方可执行，同时保留完整回滚快照

## 第十步：终极决策思维导图

按以下顺序逐项决策：

1. **单 Agent 能搞定吗？**（含视角异构检查）→ 能则止步
2. **拆分后需要频繁"讲背景"吗？** → 需要则不拆（尝试压缩）；不需要则进入下一步
3. **成本账算过了吗？**（单体基线 vs 多智能体预估）→ 比值 <1.2 不拆；>1.5 成立
4. **黑盒独立还是围着白板协作？**
   - 黑盒独立 → 流程序列已知？是 → **编排者**；否（事件驱动）→ **Bus**
   - 围着白板（写竞争/累积快照）→ **Shared State**（预先设计终止条件与版本锁）
5. **一次性派遣还是持久心流？** → 一次性用**编排者**；持久心流升级为 **Teams**
6. **质量闸门装在哪？** → 按第五步装配生成-验证器
7. **写入冲突怎么解？** → 按第六步选择协议（单点串行/物理分区/乐观锁）
8. **将来可能怎么变？** → 参照第七步（长期演进/降级）与第八步（短期自适应）
9. **人在哪介入？** → 按第九步预留待决队列与审批接口
