# iter-55：需求澄清继续点与持久化回复

## 实现

- 新增 `pm_clarification.py`，问题以独立编号绑定原 PM、任务和设备，保存选项、原截止时间及需求细化继续点。两轮上下文、已消费回答历史及最终细化任务均持久化。
- 支持原 Linux 主机原路径的规划前澄清恢复；已保存回答直接消费，第二题等待中退出仍恢复第二题，不重问第一题，不延长原等待或全局时限。
- 回复先写检查点，再唤醒 PM 并确认。错身份、空/无效问题编号、不同回答、过期和停止后的新回复拒绝。相同回复重试返回原确认，旧题回复不落到新题；终态只允许确认已保存回答。写盘失败停止并不暴露未提交回答。
- Secretary 根据持久化归属查询和转发，不依赖 `_pm_worker_map`；Station 与 Worker 共用查询/回复实现。普通进度变化不使问题查询失败，归属变化仍拒绝，最新停止/交付状态禁止新回复。
- 任务详情提供查看待回复问题、原截止时间、保存回复入口。断网、失败或确认丢失保留草稿和原问题编号；新题不会改绑旧草稿；迟到结果不更新其他任务。
- PM 线程支持读取当前问题、保存成功后读取下一题和失败保留输入。节点确认丢失后重试可补记聊天回答，并发重试只记一次。多对话线程 API 透传问题编号并返回真实成功/失败。
- Telegram 选项绑定问题编号和选项索引；旧无编号按钮拒绝。删除把 approve/abort 文本误当作继续/取消的通用按钮。测试模拟所有 Bot 网络，不发送真实消息。
- 无中央数据库 schema 迁移，仍为 v5；设计清单增加澄清模块和专项测试，共 121 条目。

## 限制与下一轮

支持的是规划前需求细化的两轮继续点；旧格式、任意执行阶段澄清、暂停后继续、本地未知工具执行、Windows 与跨机迁移仍不支持。已停止/交付任务的重复回复确认需要原 PM 实例仍可访问；不在秘书离线暂存回答。旧客户端须升级并带问题编号。

下一轮优先完善暂停后继续和在途结果的可恢复语义，准备真实模型/实际多机故障验收。模型、工具执行内容在本轮测试中为模拟；生产恢复切换和 72 小时持续运行仍未验收，不能据此宣布 1.0。
