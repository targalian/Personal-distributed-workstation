# 采用 Station 独立入口与 Secretary 动态激活架构

_来源：4bfc5f2 → 0eacfc9 提交周期内记录的编码计划——内容为规划时意图，实现可能滞后或有出入。_

**状态：** accepted

## 背景
原有的 `secretary` 模式在启动时即加载所有重型组件（项目管理、编排器、模型路由等），导致轻量级场景（如仅作为网格节点或基础监控）启动慢且资源占用高。同时，用户希望有一个更轻量的默认入口，并能按需通过 Web UI 激活完整功能。

## 决策驱动
- 降低轻量级场景的资源开销与启动时间
- 提供渐进式功能体验（先基础后完整）
- 保持向后兼容性

## 备选方案
- **保留单一 secretary 入口，内部懒加载组件** _（已否决）_ — 优点：代码结构简单，无需维护两种控制器状态；缺点：FastAPI 路由通常在启动时注册，动态增删路由复杂；初始内存 footprint 仍较大；不符合“独立入口”的清晰边界需求
- **拆分为两个完全独立的进程/服务** _（已否决）_ — 优点：隔离性最好，故障互不影响；缺点：增加了部署复杂度（需管理两个进程）；共享状态（如数据库连接、发现服务）需要同步或重复初始化；违背了“同进程激活”的便捷性初衷
- **新建 StationController 支持动态激活 Secretary 组件** — 优点：默认轻量启动；通过 API/Web UI 按需加载重型组件；复用现有基础设施代码；单进程管理简化部署；缺点：控制器状态管理变复杂（需处理激活/停用时的路由动态挂载与组件生命周期）

## 决策
引入 `station` 角色及 `StationController`。该控制器默认仅加载基础基础设施（DB、发现服务、共享文件夹、Station Director），不加载项目管理等重型组件。通过 `POST /api/station/activate-secretary` 接口在同进程中动态实例化 Secretary 组件并动态挂载相关 FastAPI 路由。Web UI 默认展示 Station 视图，提供一键激活按钮。保留旧的 `secretary` 命令行参数以维持向后兼容。

## 影响
1. 默认启动速度显著提升，资源占用降低。
2. 系统架构变为“基础层 + 可选扩展层”，需在 `StationController` 中仔细管理组件的生命周期（激活/停用）。
3. FastAPI 应用需支持动态路由注册（`include_router`/`remove_router`），增加了框架使用的复杂度。
4. 前端需适配新的状态逻辑（显示/隐藏 Tabs，切换激活按钮状态）。
