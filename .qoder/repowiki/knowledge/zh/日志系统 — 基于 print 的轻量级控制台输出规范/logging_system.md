## 1. 概述
本项目未引入第三方日志框架（如 `logging`、`loguru` 或 `structlog`），而是采用 Python 内置的 `print()` 函数作为唯一的日志输出机制。这种设计旨在保持系统的轻量级和零配置启动，特别适用于分布式节点间的快速调试与控制台监控。

## 2. 核心实现与约定
### 2.1 输出格式
所有日志输出严格遵循 `[模块名] 描述信息: {变量值}` 的格式。模块名前缀用于区分日志来源，便于在混合输出的控制台中快速定位问题模块。

**常用模块前缀：**
- `[Station]` / `[Secretary]`：中心控制节点
- `[Worker]`：工作节点
- `[AgentRuntime]`：智能体执行引擎
- `[ModelRouter]`：模型路由与降级链
- `[BotGateway]`：外部消息通道（微信/Telegram）
- `[Preflight]`：启动自检

### 2.2 关键路径覆盖
根据 `CODE_REVIEW_GUIDE.md` 规范，以下场景必须包含日志输出：
- **生命周期事件**：服务启动、停止、角色激活/停用。
- **网络通信**：UDP 发现新设备、HTTP 注册成功/失败、心跳异常。
- **任务执行**：LLM API 调用（含模型名与 Token 用量）、任务状态变更、降级链触发。
- **资源管理**：共享文件夹配置报告生成、数据库路径确认。

### 2.3 敏感信息脱敏
严禁在日志中明文输出 API Key 或敏感凭证。例如在 `ModelRouter` 中，应使用 `api_key[:8]...` 的方式进行脱敏展示。

## 3. 架构决策与限制
- **无日志分级**：目前所有输出均为 INFO 级别，缺乏 WARNING/ERROR 的结构化区分。
- **无持久化**：日志仅输出至标准输出（stdout/stderr），未集成文件轮转或远程日志收集系统。
- **Uvicorn 集成**：在 FastAPI/Uvicorn 启动时，通过 `uvicorn.Config(log_level="warning")` 抑制了框架自身的底层 HTTP 日志，确保控制台仅显示业务逻辑相关的 `print` 输出。

## 4. 开发者规范
1. **统一入口**：禁止直接使用 `logging` 模块或第三方日志库，保持技术栈统一。
2. **异常捕获**：在 `try-except` 块中捕获异常后，必须通过 `print(f"[模块] 错误描述: {e}")` 输出具体原因，避免静默失败。
3. **性能考量**：避免在高频循环（如 UDP 广播循环）中输出过多日志，以免阻塞 I/O 或刷屏影响观察。
