## 1. 核心系统与策略
LAN Mesh 项目目前**未集成专用的日志框架**（如 `logging`、`loguru` 或 `structlog`）。系统的可观测性主要依赖于以下两种机制：
- **标准输出 (`print`)**：用于记录应用层的生命周期事件、状态变更、错误提示和调试信息。所有模块均使用内置的 `print()` 函数，并采用统一的 `[组件名]` 前缀格式。
- **Uvicorn 内置日志**：在启动 HTTP 服务时，通过 `uvicorn.Config` 将日志级别设置为 `warning`，以抑制底层 Web 服务器的常规访问日志，仅保留警告和错误信息。

## 2. 关键文件与实现
- **`lan_mesh/worker.py`**: 大量使用 `print(f"[Worker] ...")` 记录注册、心跳、PM Agent 状态及子进程管理事件。
- **`lan_mesh/station_controller.py`**: 使用 `print(f"[Station] ...")` 记录 Secretary 模式激活、Bot 通道加载及主机发现状态。
- **`lan_mesh/secretary.py`**: 使用 `print(f"[Secretary] ...")` 记录模型路由加载、任务编排器初始化及数据库操作。
- **`lan_mesh/discovery.py`**: 在 UDP 广播监听循环中使用 `print(f"[发现] ...")` 记录端口绑定失败、回调异常等网络层事件。
- **`lan_mesh/preflight.py`**: 实现了 `_safe_print` 辅助函数，用于在启动自检阶段处理不同终端环境的编码兼容性（如 ASCII 回退），确保自检报告的可读性。
- **`main.py`**: 作为入口点，负责解析参数并启动对应角色，本身不产生日志，但依赖各控制器的 `start()` 方法输出启动信息。

## 3. 架构约定与规范
- **标签化前缀**：所有手动输出的日志均遵循 `[ComponentName] Message` 格式，例如 `[Worker]`、`[Station]`、`[Secretary]`、`[发现]`、`[BotGateway]`。这种约定使得在混合输出流中可以通过文本过滤快速定位特定模块的信息。
- **静默生产环境倾向**：通过将 Uvicorn 的 `log_level` 硬编码为 `"warning"`，系统倾向于在生产运行时保持控制台整洁，仅暴露应用层的关键状态变化。
- **异常处理中的日志**：在 `try-except` 块中捕获异常后，通常直接使用 `print` 输出错误摘要（如 `print(f"[Worker] 注册失败: {e}")`），而非抛出异常或记录堆栈跟踪。

## 4. 开发者指南
- **输出规范**：新增功能时，请继续使用 `print(f"[模块名] 描述信息")` 格式。避免使用裸 `print`，务必添加模块前缀以便追踪。
- **日志级别模拟**：由于缺乏正式框架，开发者需自行判断输出的重要性。关键错误（如启动失败）应清晰标注，常规状态更新（如心跳成功）在高频触发时应考虑降低输出频率或仅在调试时开启。
- **未来演进建议**：随着系统复杂度增加（特别是多 Agent 协作场景），建议引入 `logging` 模块或 `loguru`，以支持结构化日志、文件轮转及更精细的级别控制（DEBUG/INFO/WARNING/ERROR）。当前 `print` 方式在并发高或长时间运行时可能导致控制台溢出且难以持久化分析。
