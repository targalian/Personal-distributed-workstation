# 多智能体协作架构师 — 扩展参考

## 1. 成本-收益速算实操指南

### 1.1 基线成本计算示例

```
场景：单智能体处理一个需读取 20 个文件、调用 15 个工具的复杂任务

基线计算：
  - 首次加载上下文：20 文件 × 平均 2000 tokens = 40,000 tokens
  - 工具结果回填：15 次 × 平均 500 tokens = 7,500 tokens
  - 压缩/摘要迭代（预估 3 轮）：
    每轮压缩后保留 60% → 40,000 × 0.6³ ≈ 8,640 tokens
    但每轮压缩本身消耗 ~2,000 tokens（摘要生成）
  - 基线总成本 ≈ 40,000 + 7,500 + (3 × 2,000) + 8,640 = 62,140 tokens
```

### 1.2 多智能体成本计算示例

```
拆分为 1 编排者 + 3 子 Agent：

通信开销：
  - 编排者向每个子 Agent 发送任务描述 + 必要上下文：~3,000 tokens × 3 = 9,000
  - 每个子 Agent 返回结果：~2,000 tokens × 3 = 6,000
  - 编排者汇总 + 决策：~3,000 tokens
  - 验证器回路（预估 1 轮）：~4,000 tokens
  - 多智能体总成本 ≈ 22,000 tokens

比值 = 22,000 / 62,140 ≈ 0.35 → < 1.2，但质量无显著提升 → 不拆
```

### 1.3 拆分成立的示例

```
场景：需同时审查 5 个独立微服务的安全漏洞，每个微服务代码量 10,000+ tokens

基线（单智能体串行）：
  - 5 个微服务 × 10,000 tokens = 50,000 tokens（仅代码）
  - 每次审查需加载安全规则 + 上下文 = ~60,000 tokens
  - 压缩迭代 5 轮 × 3,000 tokens = 15,000
  - 基线 ≈ 125,000 tokens

多智能体（5 并行子 Agent）：
  - 每个子 Agent 独立加载 1 个微服务 + 安全规则 = ~12,000 tokens × 5 = 60,000
  - 编排者汇总 = 5,000 tokens
  - 多智能体总成本 ≈ 65,000 tokens

比值 = 65,000 / 125,000 = 0.52 → < 1.2，但延迟从 5× 降至 1× → 天然并行性成立
```

### 1.4 延迟模型对比

| 模型 | 公式 | 适用场景 |
|------|------|----------|
| 串行链 | N × 单次 LLM 延迟 | 编排者-子Agent 串行调用 |
| 并行扇出 | Max(子任务延迟) | Teams / Bus 并行处理 |
| 混合 | Σ(串行段) + Max(并行段) | 编排者 + 并行子任务 |

## 2. 模式选型决策示例

### 2.1 生成-验证器场景

```
任务：生成 SQL 查询语句

前置检查：
  ① 生成物无副作用？→ 是（SQL 仅生成文本，不执行）
  ② 验证标准可机器执行？→ 是（可用 EXPLAIN 验证语法 + 沙箱执行验证结果）

→ 生成-验证器可作为主流程前提条件

装配方式：编排者 → SQL 生成 Agent → SQL 验证器（语法+执行+安全检查）
最大循环：3 次
失败退路：返回语法正确但可能非最优的查询，标注"未通过安全验证"
```

### 2.2 编排者-子Agent 场景

```
任务：CI/CD 流水线（代码检查 → 构建 → 测试 → 部署）

检查：
  - 任务边界清晰？→ 是（4 个明确步骤）
  - 流程序列事先已知？→ 是（线性流水线）
  - 子 Agent 回复占主输入 >70%？→ 否（每步仅返回通过/失败 + 摘要）

→ 选择编排者模式

信息瓶颈预警监控：
  若编排者上下文使用率 >80% → 考虑将子 Agent 返回改为更精简的摘要
```

### 2.3 Agent Teams 场景

```
任务：持续维护一个大型文档库（每周更新）

检查：
  - 长期、多轮？→ 是（跨周持续）
  - 需要持续心流？→ 是（每个 Worker 负责特定文档章节的长期维护）

→ 升级为 Agent Teams

分区策略：按文档章节物理分区，每个 Worker 负责固定章节
冲突监控：文件锁冲突率 >20% → 重新划分分区边界
```

### 2.4 Message Bus 场景

```
任务：用户支持系统（工单 → 分类 → 路由 → 处理 → 通知）

检查：
  - 流程不可预测？→ 是（工单类型多样，路由分支多）
  - 事件驱动？→ 是（每个工单触发独立事件链）

→ 选择 Message Bus

死信队列监控：积压 >5% → 告警 + 人工介入
级联深度限制：最大 5 层，超出 → 截断并降级为直接处理
```

### 2.5 Shared State 场景

```
任务：多 Agent 协作编写技术方案文档

检查：
  - 需累积共同上下文？→ 是（方案各部分相互引用）
  - 多生产者写同一字段？→ 是（架构概述、技术选型等章节相互影响）

→ 选择 Shared State

版本锁设计：每章节独立版本号，跨章节引用通过版本快照
终止条件：所有章节达到"审阅通过"状态 → 冻结白板，输出最终文档
反应式死循环检测：同一章节 1 分钟内修改 >10 次 → 暂停写入，人工介入
```

## 3. 质量闸门装配详解

### 3.1 验证器设计要素

| 要素 | 说明 | 示例 |
|------|------|------|
| 验证标准 | 可机器执行的确定性判断 | 语法检查、单元测试通过、安全扫描无高危 |
| 通过阈值 | 明确的量化标准 | 测试覆盖率 >80%，0 个 Critical 漏洞 |
| 最大循环 | 防止无限迭代 | 默认 3 次，可配置 |
| 失败退路 | 超限后的兜底策略 | 返回当前最佳 + 风险标注，或转人工 |
| 熔断条件 | 验证器失效检测 | 通过率连续 3 轮 = 100% → 撤除回路 |

### 3.2 三种装配模式实现

**装配到编排者：**
```
编排者
  ├── 子Agent A → [验证器 A] → 通过？ → 汇总
  ├── 子Agent B → [验证器 B] → 通过？ → 汇总
  └── 子Agent C → [验证器 C] → 通过？ → 汇总
                                    ↓ 失败
                              重试（计数 < 最大循环）
                                    ↓ 超限
                              失败退路（Fallback）
```

**装配到 Bus：**
```
event: task.completed
  → verify.topic
    → 验证通过 → verified.event → 下游消费者
    → 验证失败 → retry.event → 重试队列
      → 重试超限 → deadletter.topic → 人工介入
```

**装配到 Teams：**
```
Worker 本地工作
  → 本地验证器（快速检查）
    → 通过 → 提交任务板（带版本号）
    → 失败 → 本地重试（不计入全局循环）
      → 本地超限 → 标记为"需协助"，提交任务板
```

## 4. 写入冲突协议实现指南

### 4.1 单点串行化实现

```
架构：
  - 写入者：唯一执行者（Write Agent）
  - 建议者：N 个分析 Agent（只读 + 提交补丁）

流程：
  1. 分析 Agent 读取当前状态 → 生成补丁建议
  2. 补丁建议提交到补丁队列
  3. Write Agent 按优先级拉取补丁 → 仲裁 → 合并 → 写入
  4. 冲突补丁：Write Agent 选择更优者，记录拒绝原因

优点：无冲突，简单
缺点：写入瓶颈在 Write Agent
适用：写入频率低、冲突概率高的场景
```

### 4.2 物理分区隔离实现

```
架构：
  - 分区规则：按文件/模块/章节边界划分
  - 每个 Agent 独占一个分区（无交叉写入）
  - 合并守门员：负责跨分区集成与一致性检查

流程：
  1. 预先定义分区边界（文件级或目录级）
  2. Agent 在各自分区内自由写入
  3. 完成后通知合并守门员
  4. 守门员检查跨分区接口一致性 → 集成 → 发布

优点：并行度高，无锁竞争
缺点：分区边界必须清晰，跨分区修改需协调
适用：微服务架构、多章节文档
```

### 4.3 乐观锁实现

```
架构：
  - Shared State 每个字段携带版本号
  - Agent 写入前读取当前版本号
  - 提交时检查版本号是否变化

流程：
  1. Agent A 读取字段 F（version=3）
  2. Agent B 读取字段 F（version=3）
  3. Agent A 写入 F（version=3 → 4）✓
  4. Agent B 尝试写入 F（version=3 ≠ 4）✗ 冲突
  5. Agent B 拉取最新 F（version=4）→ 解决冲突 → 重新写入（version=4 → 5）✓

冲突解决策略：
  - 字段级合并：对不同子字段的修改自动合并
  - 语义合并：对同一字段的修改需人工或规则仲裁
  - 最后写入者胜：仅适用于无冲突字段

优点：无锁阻塞，读不阻塞
缺点：高冲突率时重试成本高
适用：冲突率低、读多写少的场景
```

## 5. 运行时自适应实现模式

### 5.1 探索 ↔ 执行切换

```
触发条件：主线编排者遭遇复杂异常（错误率突增、重试失败）

切换流程：
  1. 冻结主线当前状态（快照）
  2. 开辟 Shared State 沙箱
  3. 派 2-3 个 Agent 讨论异常原因与解决方案
  4. 超时监控：3 轮内无收敛 → 冻结沙箱
  5. 收敛 → 将结论写回主线 → 恢复执行
  6. 未收敛 → 返回最后可用结论 + 风险标注 → 退回主线
```

### 5.2 降级收缩

```
Shared State → Message Bus 降级流程：

触发条件：Shared State 活跃度下降（T 分钟内无新写入）

降级步骤：
  1. 检测活跃度阈值（可配置，默认 30 分钟）
  2. 序列化 Shared State 为只读存档
  3. 关闭 Shared State 写入接口
  4. 启动 Message Bus，加载存档作为初始事件
  5. 通知所有 Agent 切换到事件驱动模式
  6. 保留回滚快照（可在 24 小时内回退）
```

### 5.3 质量危机动态注入

```
监控指标：
  - 输出置信度 < 阈值（可配置，默认 0.7）
  - 外部报错率 > 阈值（可配置，默认 5%）

注入流程：
  1. 监控检测到指标恶化
  2. 在当前工作流中插入生成-验证器回路
  3. 配置熔断器：连续 N 轮通过率 ≥ 98% → 自动撤除
  4. 记录注入事件与效果（用于后续调优）
```

### 5.4 并行度弹性扩缩容

```
扩容触发：任务队列深度 > 阈值（默认 10 个待处理任务）

扩容流程：
  1. 克隆 Worker 副本（基于当前 Worker 配置）
  2. 利用一致性哈希重新分配分区
  3. 新副本接管部分队列
  4. 监控整体吞吐量提升效果

缩容触发：队列深度 < 阈值（默认 2 个）且持续 M 分钟

缩容流程：
  1. 通知目标副本完成当前任务后停止接收
  2. 等待进行中任务完成
  3. 回收副本资源
  4. 重新分配其分区给剩余副本
```

## 6. 人机协作接口设计

### 6.1 待决队列（Pending Queue）

```
触发条件：
  - 生成-验证器循环超过最大迭代仍不收敛
  - 共享状态写冲突经乐观锁重试（默认 3 次）仍无法自动解决

队列条目结构：
  {
    "id": "pending-001",
    "timestamp": "2026-06-28T10:00:00Z",
    "type": "validator_deadlock" | "write_conflict",
    "context": { /* 当前状态与上下文快照 */ },
    "options": [ /* 可选解决方案列表 */ ],
    "risk_level": "high" | "medium" | "low",
    "rollback_snapshot": "snap-2026-06-28-001"
  }

处理流程：
  1. 推入待决队列
  2. 通知人类仲裁员
  3. 仲裁员查看上下文 + 选项 → 做出裁决
  4. 裁决作为最终事实写回系统
  5. 记录裁决用于后续类似场景的自动化改进
```

### 6.2 高风险模式切换审批

```
触发条件：
  - 编排者 → Shared State 沙箱（资源开销大）
  - Shared State → Bus 强制降级（可能丢失状态）
  - 任何涉及状态丢失风险的动态切换

审批流程：
  1. 系统生成切换方案报告：
     - 当前架构状态
     - 目标架构状态
     - 预估影响（资源、延迟、风险）
     - 回滚方案
  2. 推送给人类审批
  3. 人类确认 → 执行切换（带完整回滚快照）
  4. 人类拒绝 → 维持当前架构，记录原因
  5. 切换后监控期（默认 1 小时）→ 异常则自动回滚
```

## 7. 模式致命弱点检测清单

| 模式 | 检测指标 | 阈值 | 触发动作 |
|------|----------|------|----------|
| 生成-验证器 | 验证通过率 | 100% 持续 >3 轮 | 撤除验证器（已变为橡皮图章） |
| 生成-验证器 | 循环迭代次数 | 超过最大值 | 触发失败退路 / 转人工 |
| 编排者-子Agent | 子 Agent 回复占主输入比 | >70% | 压缩子 Agent 返回 / 考虑 Shared State |
| Agent Teams | 文件/模块锁冲突率 | >20% | 重新划分分区边界 |
| Message Bus | 死信队列积压率 | >5% | 告警 + 人工介入排查 |
| Message Bus | 级联事件深度 | >5 层 | 截断并降级为直接处理 |
| Shared State | 同字段无效修改频率 | >10 次/分钟 | 暂停写入 + 人工介入 |
| Shared State | 活跃度（无新写入） | T 分钟无活动 | 归档 + 降级为 Bus |
